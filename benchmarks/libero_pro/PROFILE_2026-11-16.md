# Optimized MPS profiling, 2026-11-16

`libero_goal_object` completed 100 diagnostic episodes (10 tasks, initial states 0–9)
without Worker failures or OOMs. This is a profiling sample, not full-suite
acceptance or an uninstrumented throughput measurement.

## Configuration

- Kit `0.8.0b39`, commit `0a420720788668b6b01bbd6d7a80174bc0619bdd`.
- Dedicated RTX 4090, 49,140 MiB VRAM, driver 595.71.05; 20-core CPU quota,
  72 GiB memory limit. Controller/Policy/simulator Python: 3.12.3/3.11.15/3.11.18.
- K=12, g=3, OMP=1, batch cap=1; MPS enabled with three observed clients.
  MessagePack and camera gating on; persistent connections, video and autotune off.
  Existing pinned simulator/checkpoint, bf16/SDPA, seed 7, ten settle steps,
  native horizons and eight-action chunks were retained.
- Nsight Systems 2026.5.1.161, `cuda-sw,nvtx,opengl` process-tree tracing;
  CPU sampling/context-switch collection off. External wrappers annotated existing
  spans; installed sources were unchanged. Stage timing and CUDA events were enabled.

One trace contains both roles. Capture started after the first replica completed
20 action calls, then continued until exit. The analysis uses seconds 5–35 after
capture start and covers all 12 Workers and three Policy replicas. Per-call NVTX
statistics include complete ranges inside that window. The trigger does not imply
that every replica had completed 20 warmup calls.

Across the whole diagnostic run, 2,063 successful action requests had mean server
lock wait of 102.40 ms, Policy service of 95.56 ms and client receive/wait of
199.52 ms. Client send averaged 1.53 ms and server send 0.17 ms. These statistics
use a different window from the table.

The 30-second trace contains 3,062,368 CUDA kernel events from the three Policy
processes. Their merged execution intervals cover 21.09 seconds (70.3%); summed
durations are 29.88 seconds because MPS permits overlap. This is kernel timeline
occupancy, not SM utilization. OpenGL GPU work is separate: the remaining 29.7%
must not be labelled GPU idle time.

Approximately 2.79 million `cudaLaunchKernel`, 158,220 `cudaMemcpyAsync` and
152,860 `cudaStreamSynchronize` calls motivate examining VLM launch/copy/sync
overhead alongside matrix multiplication. Tracing adds overhead; counts and
inclusive host times do not establish the gain from eliminating an API.

Prioritize VLM execution and replica queueing over connection reuse or action
postprocessing. Next compare fixed replica counts under MPS and inspect VLM
launch/copy patterns. These results do not establish compute versus bandwidth
versus host-launch bottlenecks, repeat-spread acceptance, or a 2x gain.

## Evidence and limitations

The host retains `comparison/profile-mps-20261116-r2/` under
`/root/autodl-tmp/issue21-20261108/`, including `plan.json`, launcher and wrappers,
`worker-policy.nsys-rep`, `worker-policy.sqlite`, `trace-summary.json`,
`timing-summary.json` and `evaluation/`. These are provenance paths, not durable
public links. Raw traces stay outside Git; publish durable links with PR evidence.

The first attempt (`profile-mps-20261116/`) exported while requests were active;
a roughly 36-second pause coincided with four RPC timeouts and Worker restarts.
It is excluded from the findings. The second attempt deferred export until exit
and had no recovery events.

Nested spans and parallel process sums are not additive elapsed time. Do not use
this instrumented sample against the unprofiled 8,000-episode baseline as speedup evidence.
